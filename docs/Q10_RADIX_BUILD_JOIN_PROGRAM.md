# Q10.RADIX — Per-partition radix/morsel no-shuffle hash join (program / ADR)

- **Status:** PROPOSED — scoping/design only. NOT accepted. Phase 0 is a hard kill-gate; no operator/kernel source is written past it unless Phase 0 is GO.
- **Date:** 2026-06-08
- **Author:** architect (cold-start design pass)
- **Reviewers:** TBD (perf owner)
- **Decision scope:** ONE decision — whether to commission a multi-session program that gives `EmatixHashJoinExec` a **DuckDB-style per-partition radix/morsel build hash table** so the existing no-shuffle path stops being dominated by cache contention on a single shared build, and Q10 (the lone remaining TPC-H SF=100 loss vs DuckDB) flips to a win. Full executor / join-order replacement is out of scope.
- **Relates to / contrasts with:** `docs/PV_M5_WORKSTEALING_SCAN_DECODE_PROGRAM.md` (CLOSED at Phase 0 — its kill-gate discipline is the template for §3 here). This program targets the **JOIN PIPELINE**, not decode; the two are disjoint and the kill-gate reasoning is the only thing carried over.

---

## 1. Thesis

> Q10's SF=100 loss is **not** decode and **not** the shared-build no-shuffle idea — it is that the *one* no-shuffle build we tried was a **single shared hash table** with **no per-partition locality**, so 14 probe threads thrash each other's cache lines. DuckDB does the no-shuffle join and wins because its build is **radix-partitioned into many cache-resident sub-tables**, each probe thread touching only its own partition. The program asks: can we radix-partition BOTH the build and the probe by join-key hash so each `(probe-partition, build-partition)` pair is a cache-local probe — eliminating the contention that produced the measured **+21.7%** on the shared-build attempt — or learn precisely that the radix pass over 148M probe rows costs more than the locality it buys?

### Measured evidence (ground truth — from MEMORY.md and the bench table)

1. **Q10 is the lone SF=100 loss vs DuckDB.** `docs/BENCHMARKS.md:100`: `Q10 | 3,291 | 2,691`. The logged 3,291 is the **3-engine harness** under contention; the task's ematix-only re-measure is **~2,735 ms vs DuckDB 2,691** — a **near-parity loss, ~44 ms to flip**. Every other SF=100 query is a win (`docs/BENCHMARKS.md:84-112`, 18/22 wins).
2. **The decode is at a proven floor.** ematix already beats DuckDB *and* Polars on Q01 pure decode at SF=100 (`docs/BENCHMARKS.md:91`: `Q01 | 2,361 | 2,619`). The "do not declare a floor" rule is honored *inward*: the gap is the **join pipeline**, not decode, because the decode-dominated query already wins.
3. **The hot operator is `HashJoinExec(mode=Partitioned, Inner, o_orderkey=l_orderkey)`** (`docs/PERF_Q10.md:55`, the plan). It RepartitionExec-shuffles + probes ~148M `l_returnflag='R'` lineitem rows against a ~5.7M-row `customer⋈orders` build, producing ~11.5M matches. (At SF=10 this same join is `798 ms` of summed compute / `88 ms` wall — the single largest operator in the query: `docs/PERF_Q10.md:70`, `docs/PERF_Q10.md:106`.)
4. **The shared-build no-shuffle was already tried and LOST.** SF100.6/7 (`EMAT_HJ_PARTITIONED=1`, `swap_emat_hash_join_rule.rs:48-77` strips the two `RepartitionExec`s; `EmatixHashJoinExec` builds **one shared `OnceCell<Arc<EmatHashJoiner>>`** at `emat_hash_join_exec.rs:46`/`:173-199`): **+21.7% at SF=100 Q10** (HJ_NOSHUFFLE 3443.6 ms vs STOCK Partitioned-shuffle 2828.6 ms; A/B in MEMORY). Root cause **measured**: one shared ~3.2 GB build hammered by 14 probe threads → cache contention, no per-partition locality. The concat-free interleave-gather build (committed `3d84757`, `emat_hash_join.rs:84-181`) made it **memory-viable** (single-query ~9.45 GB on a 38.7 GB box) but did **not** fix the contention.
5. **Runtime-bloom orders→lineitem pushdown also LOST**: A/B'd → **+24%** (serializes the build + a 30M-mis-sized bloom). MEMORY banks this as a NO-GO.

The recoverable quantity is small and symbolic: **~44 ms** to flip the near-parity loss; **maybe ~150-250 ms** if the join fully matches DuckDB's join structure, on top of a **~2,300 ms decode floor**. This is the **last SF=100 holdout** — the value is "18/22 → 19/22 SF=100 wins," not raw time.

## 2. THE RED FLAGS (central risks, stated up front)

This program is **presumed dead** until Phase 0 proves otherwise. There are three independent ways it dies, two of which already have measured precedent in *this exact join*:

### RF-1 — the shared-build no-shuffle already lost by +21.7%, and radix may not recover it.

The no-shuffle DIRECTION is a **proven −21.7% regression** in its only realized form. The standing MEMORY note is explicit: *"Retry the no-shuffle DIRECTION only with a per-partition radix/morsel build hash table (DuckDB-style); **sign-flip unproven**, multi-week."* The thesis is that **locality** (cache-resident sub-tables) is what DuckDB has and our shared build lacks — but that is an *inference* from DuckDB's architecture, not a measurement on our cardinalities. Phase 0 exists to convert the inference into a number.

### RF-2 — the radix pass over 148M probe rows may eat the locality gain.

Radix-partitioning is not free. To make sub-tables cache-resident we must **scatter 148M probe keys (+ their payload row-ids) into N partitions** before probing. A scatter of 148M × (8 B key + 4-8 B row-id) is **~1.8-2.4 GB of random-ish writes** into N partition buffers. If N is large enough to make build sub-tables L2-resident (≥256), the *scatter itself* has the same write-fan-out cache behavior we are trying to escape on the probe. **The known stock path (`mode=Partitioned`) already pays a 148M-row `RepartitionExec` shuffle** (`docs/PERF_Q10.md` plan) — so the honest comparison is not "radix vs nothing," it is **"radix scatter + cache-local probe" vs "RepartitionExec shuffle + DataFusion's partitioned probe."** Stock already won that comparison once (it beat the shared no-shuffle). Radix must beat *stock's shuffle+probe*, not just the shared build.

### RF-3 — DuckDB's win may be its build CARDINALITY, not its build STRUCTURE.

Q10's build is `customer⋈orders` = ~5.7M rows of **wide strings** (`c_name, c_address, c_phone, c_comment` — `docs/PERF_Q10.md:52`). DuckDB may be fast on Q10's join for reasons orthogonal to radix: a tighter customer scan, a smaller materialized build payload (it may not carry the wide strings through the join — projecting them post-join), or a better join order. **If we radix-partition a 3.2 GB build and DuckDB never materializes 3.2 GB, we will have optimized the wrong axis.** Phase 0's microbench must therefore isolate the **i64-key join mechanics** (5.7M build keys + a *narrow* payload row-id; 148M probe keys) from the wide-string materialization — and §4.4 must separately address whether the wide payload should even flow through this operator.

**Phase 0 resolves RF-1 and RF-2 directly (the microbench is the radix-vs-shared-vs-stock-proxy comparison on the real cardinalities). RF-3 is resolved partly in Phase 0 (narrow-payload isolation) and partly by a cheap profiling probe of DuckDB's Q10 plan (§3.4).**

## 3. Phase 0 — decisive de-risk spike (GO / NO-GO). THE KILL-GATE.

**Goal:** on Q10's **real cardinalities**, determine whether a per-partition radix/morsel build+probe beats both (A) the known shared-build shape and (B) a faithful proxy of the stock partitioned shuffle+probe, by a margin that — projected to the full query — brings Q10 under STOCK ~2,828 ms (SF=100 stock-partitioned wall), **with the win attributable to reduced cache-miss stalls** (perf counters), not a measurement artifact. No DataFusion, no operator, no plan rewrite. One throwaway example binary.

This mirrors `docs/PV_M5_WORKSTEALING_SCAN_DECODE_PROGRAM.md §3`: a standalone, full-cardinality, correctness-asserted, interleaved, perf-counter-attributed spike whose pre-registered kill number decides the program before any integration code.

### 3.1 The spike harness (model on `crates/ematix-flow-hash-join/examples/{hj4_salt_derisk.rs, q08_probe.rs}`)

Build **one** `main.rs` in `crates/ematix-flow-hash-join/examples/` (auto-registered; the crate is Arrow/DataFusion-free, `rand = "0.9"` is already a dev-dep — `crates/ematix-flow-hash-join/Cargo.toml:19-21`). It synthesizes Q10's real shape with seeded RNG, runs all arms interleaved per trial, asserts byte-identical match counts, and reports median wall + CPU/wall (parallel efficiency) + per-arm last-thread-finish (idle-tail) + perf-counter cache-miss attribution.

**Cardinalities (Q10 SF=100, the real shape):**
- **Build:** `n_build = 5_730_000` i64 `o_orderkey`s. Orderkeys are **unique** in the `customer⋈orders` build (orders PK survives the join), so the build is **key-unique** → the `TaggedJoinI64U32` path (`tagged.rs`) is the realistic kernel, *and* RF-3's "narrow payload" is naturally a single `u32` build-row-id. Carry an 8-byte synthetic payload per build row to model the row-id + a representative gather cost; **do not** carry the wide strings (RF-3 — those are a separate §4.4 question).
- **Probe:** `n_probe = 148_000_000` i64 `l_orderkey`s drawn so **~11.5M match** the build (hit rate ≈ 11.5M / 148M ≈ **7.8%**). Orderkey domain: lineitem `l_orderkey ∈ [1, 150M]` at SF=100; the build is 5.73M distinct orderkeys that survive the orders-date filter, so a probe key hits with probability ≈ 5.73M-surviving-with-~2-lineitems... — **calibrate the generator so the asserted match count lands within ±2% of 11.5M** (the generator's job; the *number* 11.5M is the invariant, per `docs/PERF_Q10.md:70` out-rows 1,147,084 ×100/10 scaling cross-checked against the SF=100 plan).
- **Partition counts to sweep (B):** `{14, 64, 256, 1024, 4096}`. A 5.73M-entry tagged table is **tags(1B) + keys(8B) + idx(4B) ≈ 13 B/entry × (5.73M / 0.7 load) ≈ ~106 MB** (the `TaggedJoinI64U32` SoA at `tagged.rs:94-100`, `cap = next_pow2(n×10/7)`). To get a sub-table into a **~1-2 MB L2 slice** needs `106 MB / 1.5 MB ≈ ~70` partitions minimum; to get comfortably L2-resident with headroom needs **≥256**; **1024/4096** test whether over-partitioning's scatter-write fan-out (RF-2) starts to dominate. **The sweep finding "where sub-tables go cache-resident" is the core deliverable** — without it the program has no defensible partition count.

### 3.2 The arms (paired / interleaved per trial; `paired_ab.rs` methodology)

- **Arm A — shared-build probe (the known +21.7% shape).** One `TaggedJoinI64U32` over all 5.73M build keys; spawn 14 threads, each probing a contiguous 1/14 slice of the 148M probe keys against the **one shared table**, accumulating matches. This reproduces `EmatixHashJoinExec`'s no-shuffle build (`emat_hash_join_exec.rs:173-206`) at the kernel level. **This is the baseline the radix arm must beat.**
- **Arm B — radix-partitioned build + probe, SWEPT over N ∈ {14, 64, 256, 1024, 4096}.** Two phases:
  1. **Build scatter:** hash each build key (the kernel's `splitmix64`, `tagged.rs:21`), take `top-log2(N) bits` (or low bits — pick the bits *disjoint* from the bits the in-sub-table hash uses, to avoid all keys landing in one bucket of the sub-table), append `(key, row_id)` to partition `p`. Then build **N independent `TaggedJoinI64U32` sub-tables**, one per partition (each ~`106MB/N`).
  2. **Probe scatter + local probe:** 14 threads cooperatively (a) scatter the 148M probe keys into N probe-partition buffers by the **same** radix bits, then (b) for each partition `p`, probe `probe_part[p]` against `build_subtable[p]` only — a **cache-local** probe (the sub-table fits L2). Match accumulation identical to Arm A.
     - *Two scatter strategies to try if (b) alone doesn't clear the gate:* **B-fused** = skip the explicit probe scatter; instead each of the 14 threads streams its 1/14 probe slice and, per key, computes the radix partition and probes that sub-table inline (no scatter buffer, but loses streaming locality on the sub-tables); **B-scatter** = the full scatter-then-local-probe above (pays the 2 GB scatter write but each sub-table probe is dense and cache-local). **B-scatter is the DuckDB-faithful arm; B-fused is the cheap-to-build proxy.** Report both — if B-fused already clears the gate, the scatter is unnecessary and integration is far cheaper.
- **Arm C — stock-shuffle proxy (the honest comparison for RF-2).** Model what `mode=Partitioned` already does: **14 build sub-tables** (one per the 14 hash partitions the `RepartitionExec` would produce) + a **probe scatter into 14 partitions** + per-partition probe. This is Arm B at **N=14** but framed as "what stock's shuffle+probe costs," so the gate can check radix(B, best N) vs **both** shared(A) **and** the stock-equivalent(C). *If C ≈ A, then stock's win over the shared no-shuffle was something the kernel proxy doesn't capture (e.g. DataFusion's probe-side parallel pipeline overlap) and the spike is measuring the wrong thing — a flag in itself.*

All arms produce the **identical asserted match count** (a `black_box`ed sum of `build_row_id`s over all matches is the cheapest order-independent checksum; assert equal across A/B/C every trial — the `hj4_salt_derisk.rs` correctness-assert discipline). Report median wall, CPU/wall, idle-tail, and **cache-miss counts** per arm.

### 3.3 The kill number (hard gate)

Let `W_A` = Arm A median wall, `W_B*` = best Arm-B median over the N-sweep, `W_C` = Arm C median. The full-query stock-partitioned SF=100 wall is **~2,828 ms** and the hot join is the dominant operator (at SF=10 it is `798/2184 ≈ 37%` of summed compute; assume the SF=100 join is a **similar-or-larger** fraction — Phase 0 does **not** need the exact fraction, only the *kernel-level ratio*, because the join-kernel time is what radix changes).

> **GO** iff **ALL** of:
> 1. `W_B* ≤ 0.80 × W_A` (radix recovers the full +21.7% shared-build penalty *and then some* — i.e. radix must be at least ~20% faster than the shared build, because the shared build is what loses by 21.7% and we need to land **under** stock, not merely back at the shared-build number); **AND**
> 2. `W_B* < W_C` by a paired sign test **p < 0.05** (radix beats the stock-shuffle-equivalent — without this, the existing `mode=Partitioned` is already as good and there is nothing to ship); **AND**
> 3. The `W_B*` advantage is **attributed to reduced cache-miss stalls** — Arm B's L2/L3 cache-miss count per probe is materially below Arm A's (perf counters: `perf stat -e LLC-load-misses,l2_rqsts.miss` on Linux, or `Instruments`/`dtrace` on macOS; at minimum the **CPU/wall parallel-efficiency** of B must exceed A's, since contention shows up as stalled cycles), **not** a measurement artifact (recall PV.4's "−16%" prebuilt-slice artifact and the HJ.3 "2.36× microbench" cache-hot artifact — `q08_probe.rs` header).
>
> **AND** the sweep must **identify a stable best-N** (the win is not a single lucky partition count — at least two adjacent N values in the sweep clear gate 1, establishing a plateau, so the integration has a defensible partition-count rule).

- **All four clear → GO.** Proceed to §4. The doc records the winning N (and whether B-scatter or B-fused won — decides integration cost) and the projected full-query Q10 wall = `2828 − (W_A − W_B*) × kernel_fraction`.
- **`W_B*` beats A but is ≥ `W_C` (radix beats shared but not stock's shuffle) → NO-GO.** The stock `mode=Partitioned` path is already at least as good; the no-shuffle direction has no headroom even with radix. Ship nothing; record the number. *This is the most likely NO-GO* given RF-2 (stock already beat the shared no-shuffle).
- **`W_B*` between `0.80×W_A` and `W_A` → MARGINAL → default NO-GO.** A < 20% kernel win that must fight DataFusion's distribution contract (§4, R-DF) and re-introduce a radix scatter that competes with the shuffle DataFusion already does well is not worth the multi-week spend on a ~44 ms full-query flip. Record the number.
- **`W_B*` ≥ `W_A` at every N (radix never beats the shared build) → NO-GO, thesis FALSIFIED.** The partition scatter over 148M eats the locality gain (RF-2 confirmed); DuckDB's Q10 edge is *not* reproducible as a radix build in our kernel and must be its build cardinality / join order (RF-3) — redirect to §3.4's DuckDB-plan probe and a join-order / projection-pushdown lever instead. A valid, cheap-to-learn outcome.

**NO phase past Phase 0 runs unless §3.3 returns GO.** Same single-spike kill discipline that closed PV.M.5 at Phase 0.

### 3.4 RF-3 cross-check (cheap, parallel to the spike — ~half a day)

Independently of the kernel spike, **profile DuckDB's actual Q10 SF=100 plan** to confirm radix is even the right axis:
- `EXPLAIN ANALYZE` the DuckDB Q10 at SF=100 (or SF=10 if 100 is impractical) and read: (a) does DuckDB carry the **wide customer strings** through the hot `o_orderkey=l_orderkey` join, or project `c_custkey` only and re-join the strings after? (b) what is DuckDB's **build side** for that join (does it build on the 5.7M `customer⋈orders` or on the 148M lineitem with a different order)? (c) does its profile show a **radix/partition** step?
- **If DuckDB does NOT materialize the wide build** (projects custkey, re-attaches strings post-aggregate — note Q10's group-by is on `c_custkey + 6 passthrough cols`, `docs/PERF_Q10.md:52`, so the strings are only needed at the *very top*), then the cheapest Q10 win is **not radix at all** — it is a **projection-pushdown / functional-dependency lever** (group by `c_custkey`, re-attach the 6 wide cols after the agg) already noted as the SF=10 dominant lever (`docs/PERF_Q10.md:33`, `:99`). **That lever is single-edit-class, not multi-week**, and §6 weighs it as the cheaper alternative.

This §3.4 probe can **flip the whole program to a cheaper path before the kernel spike even finishes** — run it first.

## 4. Architecture (meaningful ONLY if Phase 0 is GO)

The hard part is reconciling an **internal radix pass** with (a) DataFusion's `ExecutionPlan` distribution contract and (b) the existing `EmatixHashJoinExec` (`emat_hash_join_exec.rs`). Five sub-problems.

### 4.1 Where the radix pass lives vs the RepartitionExecs

The current no-shuffle swap **strips** the two `RepartitionExec`s (`swap_emat_hash_join_rule.rs:66-77` `strip_shuffle`) and declares `UnspecifiedDistribution` so `EnforceDistribution` inserts no shuffle (`:48-59`). The radix design **keeps that strip** — but instead of probing one shared table, the operator does its **own radix scatter internally**, replacing the work the `RepartitionExec` used to do. The distinction from stock: a `RepartitionExec` hash-shuffles **whole batches across the tokio runtime** (cross-thread channels, batch re-chunking); the internal radix scatter partitions **raw key+row-id arrays in-process** into cache-sized sub-tables with no batch envelope. Whether that in-process scatter actually beats the runtime shuffle is **exactly RF-2 / gate 2** — so this architecture is only built if Phase 0's Arm B beat Arm C.

### 4.2 Build/probe radix symmetry + the morsel-driven build over 14 input partitions

- **Build (LEFT) side** still drains via the parallel `try_join_all` over `left.output_partitioning().partition_count()` partitions (`emat_hash_join_exec.rs:176-187`, the SF100.6-v2 parallel-drain that fixed the single-threaded-build wall). The change: instead of `EmatHashJoiner::try_build` producing **one** table (`emat_hash_join.rs:153-171`), it produces **N radix sub-tables**. The build scatter (hash key → partition by `radix_bits`) happens *during* the existing key-gather pass (`emat_hash_join.rs:117-135`) — that pass already walks every build key once to build the contiguous `keys` slice; it appends `(key, global_row_id)` to `partition_buffers[p]` instead, then builds N `TaggedJoinI64U32`s. **Morsel-driven build:** the 14 drain tasks each scatter their own batches into thread-local partition buffers, merged at the end (or N atomic-appended shared buffers) — this is the standard DuckDB morsel build and maps cleanly onto the existing parallel drain.
- **Probe (RIGHT) side** must radix-partition by the **same** `radix_bits`. Each `execute(partition)` stream (`emat_hash_join_exec.rs:202-206`) currently probes its right batches against the shared table. The change: each probe batch's keys are scattered by `radix_bits` and each scattered run probes its matching sub-table. **Symmetry invariant:** build partition `p` and probe partition `p` use **bit-identical** radix extraction (the same `splitmix64` + the same bit-slice) so a key that built into sub-table `p` is probed only against sub-table `p`. A TDD test asserts a key present in the build is found regardless of which sub-table it lands in (the `tagged.rs` `unique_build_probe_matches` test, generalized across the scatter).

### 4.3 Output partitioning + materializing the 11.5M output

- **Output partitioning:** `EmatixHashJoinExec` declares the **probe side's partitioning** as output (`emat_hash_join_exec.rs:59-60`, CollectLeft semantics). With internal radix, the *probe input* partition count is unchanged (14), so **output partitioning stays = probe partitioning** — the radix is an *internal* detail invisible to the plan, which is the whole reason it can replace the stripped `RepartitionExec` without violating `EnforceDistribution`. The downstream 7-col `AggregateExec` (`docs/PERF_Q10.md:51`) still sees 14 partitions. **Decision: radix is operator-internal; PlanProperties unchanged from today's no-shuffle.**
- **Output gather of 11.5M matches:** reuse the existing concat-free gather (`emat_hash_join.rs:207-259`): per probe batch, the kernel emits `(probe_row_idx, build_row_idx)` pairs; build-side columns gather via `interleave` over the un-concatenated build batches (`:225-251`), probe-side via `take`. **The radix scatter must preserve each match's `(probe_batch, probe_local_row)` and `(build_global_row)` so the gather is unchanged** — i.e. the scatter carries row-ids, not just keys, exactly as the `ProbeMatch` struct already does (`table.rs:85-89`). This is why the build payload in Phase 0 is a `u32` row-id, not the wide strings: the strings are gathered *post-match* by `interleave`, never partitioned.

### 4.4 The 3.2 GB wide build payload — must NOT stack, and arguably must NOT flow

- **Memory (the 3.2 GB build must not stack):** the concat-free build (`emat_hash_join.rs:84-181`, commit `3d84757`) keeps the wide payload as the **original un-concatenated `Vec<RecordBatch>`** and gathers per-match via `interleave`. Radix changes only the **key+row-id** tables (N × ~`106MB/N` = ~106 MB total, same as today's one table — **partitioning does not increase build memory**, it slices it). The wide 3.2 GB payload is **referenced, never copied** into partitions (the `Arc`-backed columns, `:175`). **Invariant: peak build RSS under radix ≈ peak build RSS today** (~9.45 GB single-query); the radix sub-tables are a re-slicing of the existing ~106 MB key table, not a second copy of the payload. A memory gate (§5) confirms no ballooning.
- **RF-3 / should the wide payload flow at all:** if §3.4 finds DuckDB projects `c_custkey` through the join and re-attaches strings post-agg, then the **bigger** Q10 win is to **not carry `c_name/c_address/c_phone/c_comment` through the 148M-row probe** — group by `c_custkey` (+ the few narrow cols), aggregate, then join the 5 wide strings onto the **381k output groups** (`docs/PERF_Q10.md:71`). That is the functional-dependency simplifier (`docs/PERF_Q10.md:33`) and it shrinks the build *and* the agg key, independent of radix. **Architecture note: radix and the projection-pushdown are orthogonal and composable; if Phase 0 GOes, still consider the projection lever as the cheaper first ship** (§6).

### 4.5 Skew + the existing overflow machinery

Radix-by-hash naturally balances unless a few orderkeys are pathologically hot. Q10's build is orderkey-unique so per-key chains are length-1 — **no build-side skew**. The probe side (lineitem) has ~2 lineitems/order on average, mild and uniform. The existing skew detection (`skew.rs` `observe`, `OverflowTable`) is **inert** here (no key clears `MIN_HOT_ABSOLUTE=100` on a unique build) and can be left out of the radix path in v1. *If a future non-Q10 shape has a hot key, the radix partition for that key's hash would be oversized — but that is a Phase-3 generalization concern, gated separately.*

## 5. Phased plan (each default-OFF behind a flag; each gated)

Shared gate for every code phase (house discipline, mirrors PV.M.5 §5):
- **22q SF=100 interleaved A/B** (the strict protocol: `scripts/bench/strict_ab.sh`, `caffeinate`/`taskpolicy`, discard-first, median-of-medians; `EMAT_HJ_RADIX=1` ON vs OFF), ≥ the protocol's trial count, paired sign test. **SF=100 is the target — SF=10's 88 ms join is below the noise floor for a ~44 ms-class lever, and MEMORY warns SF=10 noise is ±5-10%/query.**
- **`tpch_validate` 22/22 vs DuckDB at SF=1/10/100 — row counts** (the radix join is integer-exact; no float-determinism concern here, unlike PV.M.5 — orderkey matching is order-independent for the *match set*, and the downstream SUM(revenue) is grouped by custkey, but verify the SF=100 cell-by-cell match anyway).
- **No TPC-H-specific hardcoding** — radix bit-count is a function of `build_row_count` (→ target sub-table ≤ L2), never query identity. The partition-count rule from Phase 0's sweep is `N = next_pow2(build_bytes / L2_target)`, parametric.
- **Codegen-tax check:** the radix kernel lives in `ematix-flow-hash-join` (the Arrow/DataFusion-free crate, `lib.rs:1-12` rationale), so the LLVM codegen tax stays local to the consumer — flag-OFF binary vs prior, 22q SF=100 A/B ≤ noise.

- **Phase 0 — de-risk spike (GO/NO-GO).** §3. The kill-gate + the §3.4 DuckDB-plan probe (run §3.4 FIRST — it may flip to the cheaper projection lever before the spike completes). Nothing below runs unless GO **and** §3.4 doesn't surface a cheaper win.
- **Phase 1 — radix sub-table kernel in `ematix-flow-hash-join`, unit-tested only.** Add a `RadixTaggedJoin` (N `TaggedJoinI64U32` sub-tables + a `radix_bits` scatter; `tagged.rs` is the per-sub-table substrate, unchanged). TDD: match-set equality vs a single `TaggedJoinI64U32` over the same keys; symmetry (build-partition `p` ⟺ probe-partition `p`); null-key skip across the scatter; the Phase-0 Arm-B loop expressed through this kernel still clears §3.3 (the abstraction added no overhead). ## 6. Risks & kill criteria + which prior finding each addresses

- **R-shared (RF-1) — radix may not flip the shared-build −21.7%.** Addresses the **SF100.6/7 no-shuffle +21.7%** measured NO-GO. **Kill:** Phase 0 gate 1 (`W_B* ≤ 0.80×W_A`). - **R-scatter (RF-2) — the 148M-row radix scatter eats the locality gain, and stock's `RepartitionExec` shuffle already does this work well.** Addresses the fact that **stock `mode=Partitioned` already beat the shared no-shuffle** (2828 < 3443). **Kill:** Phase 0 gate 2 (`W_B* < W_C`, the stock-shuffle proxy, p<0.05). - **R-cardinality (RF-3) — DuckDB's Q10 edge is build cardinality / projection / join order, not radix.** Addresses the risk of optimizing the wrong axis. **Mitigation/kill:** §3.4 DuckDB-plan probe **before** the spike; if DuckDB projects custkey through the join, redirect to the **projection-pushdown / functional-dependency simplifier** (`docs/PERF_Q10.md:33,99`) — a **single-edit-class lever** that is the *cheaper GO/NO-GO path* and may flip Q10 without any radix work.
