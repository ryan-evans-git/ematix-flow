# Reproducing the benchmarks

Every performance number ematix-flow publishes is meant to be reproduced
by anyone, on their own hardware, from this repository. This page is the
single entry point; [`scripts/bench/README.md`](scripts/bench/README.md)
documents the full measurement protocol behind it.

> **Why you can trust the inputs.** TPC-H data is generated by
> [`tpchgen-rs`](https://github.com/clflushopt/tpchgen-rs) via the
> `tpch_generate` example — it is **byte-for-byte identical to the
> canonical TPC-H `dbgen`**, just ~10× faster. No hand-tuned or
> cherry-picked datasets: you generate the same bytes we do.

## One command

From a clean checkout, on a machine with a Rust toolchain and Python:

```bash
make bench-repro                       # SF=1, ematix vs duckdb
```

This generates the SF=1 dataset, builds the release benchmark binary,
runs each engine through the strict 22-query protocol in its own isolated
process, and writes per-engine summaries plus an ematix-vs-duckdb verdict
table under `bench-results/repro-sf1/`.

Scale it up or change the engine set with variables:

```bash
make bench-repro SF=10                          # SF=10
make bench-repro SF=1  ENGINES="ematix polars"  # a different comparison
make bench-repro SF=100                          # ~150 GB scratch, hours
```

`SF`, `ENGINES`, and `BENCH_OUT` are the only knobs. Engines are looked up
by name in the strict runner, so as new comparison engines are wired in
(ClickHouse is in progress), they become available here by adding them to
`ENGINES` — no change to this entry point.

## Prerequisites

- **Rust** (stable) — builds the engine and the data generator.
- **Python 3.11+** with the comparison engines you want to run:
  `pip install duckdb polars pyarrow`.
- **Disk / RAM** — SF=1 is trivial; SF=10 wants a few GB; **SF=100 needs
  ~150 GB scratch and is memory-sensitive** (data approaches RAM size).
  See the scale guidance in `scripts/bench/README.md`.

## What "one command" runs, step by step

If you'd rather drive it yourself (or reproduce a specific published
figure), the entry point is equivalent to:

```bash
# 1. Generate the dataset (byte-for-byte dbgen-equivalent).
cargo run --release -p ematix-flow-core --example tpch_generate -- \
    --sf 1 --out examples/tpch/data/sf1

# 2. Build the release benchmark binary.
cargo build --release --example tpch_triangulation_bench --features triangulation

# 3. One isolated, solo pass per engine (engines never share a process —
#    RAM/thermal isolation is part of the protocol).
scripts/bench/strict_22q.sh --sf 1 --engine ematix --isolate --trials 10 \
    --out bench-results/repro-sf1/ematix
scripts/bench/strict_22q.sh --sf 1 --engine duckdb --isolate --trials 10 \
    --out bench-results/repro-sf1/duckdb

# 4. Per-query verdicts with a 2×σ noise bar (no claim inside the bar).
python3 scripts/bench/strict_diff.py \
    --a bench-results/repro-sf1/ematix/strict-22q-summary.md \
    --b bench-results/repro-sf1/duckdb/strict-22q-summary.md \
    --label-a ematix --label-b duckdb \
    --out bench-results/repro-sf1/verdicts.md
```

Concurrent-stream throughput (QPH) and the distributed 4-node mesh
comparison have their own drivers — `scripts/bench/strict_throughput.sh`
and `scripts/tpch-bench-multi.sh` — documented in
[`scripts/bench/README.md`](scripts/bench/README.md) and
[`docs/BENCHMARKS-DISTRIBUTED.md`](docs/BENCHMARKS-DISTRIBUTED.md).

## Platform notes — read before comparing to our published numbers

The strict protocol was designed on Apple Silicon and encodes discipline
that matters for a fair comparison:

- **Thermal gating.** On macOS the runner blocks new invocations while
  `pmset -g therm` reports throttling. On Linux there is no equivalent
  gate — run on an otherwise-idle machine, and prefer a fixed CPU
  governor (`performance`) to keep frequency stable.
- **Page-cache policy.** Runs are warm-cache by default (first invocation
  discarded). At SF=100 the cache policy dominates the noise floor — state
  which you used.
- **Settled machine.** Engine-vs-engine verdicts are only quotable from a
  machine that has been idle ≥45 min; sustained thermal soak slows
  bandwidth-heavy queries disproportionately. Interleaved A/B runs are
  immune. See the "settled-machine rule" in `scripts/bench/README.md`.

Because of this, **absolute times will differ across machines** — what
reproduces is the *relative* standing between engines on the same
hardware under the same protocol. If you get a materially different
*verdict* (not just different absolute times) on settled, idle hardware,
please [open an issue](https://github.com/ryan-evans-git/ematix-flow/issues)
with your `env.json` (the runner writes one into each output dir) — that's
exactly the kind of report that keeps the numbers honest.
